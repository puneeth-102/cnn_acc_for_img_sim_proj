SPECIFICATION DOCUMENT
RISC-V SoC with Hardware-Accelerated CNN-Based Image Similarity and Anomaly Detection
Implementation-ready specification for Kiro / RTL development
0. Document Purpose
This document converts the current project architecture into an implementation-oriented specification that can be supplied to Kiro for RTL generation and integration. It defines the system architecture, control path, data path, 2-master × 8-slave memory-mapped interconnect, memory map, registers, signals, errors, interrupts, operation sequence, and verification requirements.
Important architecture terminology: the conceptual system bus is specified as a 32-bit memory-mapped bus. The faculty-provided interconnect generator may be used as the RTL implementation mechanism; this document does not redefine the conceptual bus as AXI unless the implementation interface requires it.
1. Introduction
1.1 Project Title
Design of a RISC-V SoC with a Hardware-Accelerated CNN-Based Image Similarity and Anomaly Detection Engine
1.2 System Description
The proposed project implements a RISC-V based System-on-Chip for embedded image similarity and anomaly detection. A small grayscale image is processed by a lightweight CNN accelerator to generate a compact embedding. The generated embedding is compared against stored reference embeddings. The distance/anomaly engine calculates the distance to each reference, selects the minimum distance, and compares it against a programmable threshold to classify the input as MATCH or ANOMALY.
The RISC-V processor is the system controller. Three project-specific IPs are integrated: (1) CNN Feature Extraction Accelerator, (2) Distance/Anomaly Scoring Engine, and (3) DMA Controller. The SoC also contains faculty-provided RISC-V, IMEM, DMEM, UART, Timer and GPIO.
1.3 Problem Statement
Software-only CNN inference on a general-purpose processor requires many multiply-accumulate operations and can increase latency and CPU utilization. Dedicated hardware is therefore used for CNN feature extraction and distance scoring while the RISC-V performs configuration, sequencing and result management.
1.4 Objectives
Integrate the faculty-provided RISC-V processor into a complete SoC.
Provide memory-mapped access to all peripherals and project IPs.
Implement a lightweight CNN feature-extraction accelerator.
Support INT8 image and weight processing.
Generate a compact embedding vector from the input image.
Compare the query embedding with multiple reference embeddings.
Support a configurable distance metric and anomaly threshold.
Implement DMA-based movement of image, weight and embedding data.
Provide interrupt-based completion notification.
Report the final classification through software/UART and optionally GPIO.
Verify hardware results against a Python/NumPy golden model.
2. Top-Level Architecture
The top-level functional blocks are:
RISC-V Core — primary system master; configures IP registers, starts operations, polls status and handles interrupts.
32-bit Memory-Mapped System Bus / Interconnect — routes transactions according to the memory map.
DMA Controller — secondary bus master for bulk data movement and a memory-mapped slave for CPU configuration.
CNN Accelerator — performs input buffering, INT8 convolution/MAC processing, pooling and embedding generation.
Distance/Anomaly Engine — performs query/reference distance calculation, minimum-distance selection and threshold comparison.
IMEM — instruction memory.
DMEM — 64-KB data memory holding input image, CNN weights, reference embeddings and generated/query embeddings.
UART, Timer and GPIO — standard SoC peripherals.

2.2 Conceptual Interconnect
The interconnect has two incoming master interfaces and eight decoded slave targets. The RISC-V normally initiates configuration and memory transactions. DMA requests bus ownership when it performs bulk transfers. A fixed-priority arbitration policy may be used, with CPU transactions retaining normal priority and DMA obtaining access according to the project arbitration policy.
Conceptual connectivity: RISC-V → Interconnect; DMA master → Interconnect; Interconnect → IMEM/DMEM/UART/Timer/GPIO/CNN/Distance/DMA-register interface.

3.1 Interconnect Generator Configuration
For the faculty-provided Python wrapper, use the 2-master × 8-slave configuration:
python3 axi_interconnect_wrap.py -p 2 8
In the wrapper naming convention, S_COUNT=2 represents the two incoming master-side interfaces, while M_COUNT=8 represents the eight outgoing slave-side interfaces. The project-level naming used in this document is M0/M1 for functional bus masters and M00–M07 for decoded slave targets to avoid ambiguity.

4.1 High-Level Control Sequence
Initialize/reset the SoC and accelerator blocks.
RISC-V configures CNN base addresses and dimension parameters.
RISC-V configures DMA source, destination, length and control.
DMA transfers image/weights into the CNN-accessible memory/data path.
RISC-V starts CNN processing.
CNN executes convolution → pooling → embedding generation.
Generated embedding is stored in DMEM.
RISC-V configures the distance/anomaly engine with query/reference addresses, count, metric and threshold.
RISC-V starts the distance engine.
Distance engine computes distances, selects minimum distance and performs threshold comparison.
RISC-V receives SCORE_DONE_IRQ or polls status and reads the result.
Result is reported through software/UART and optionally GPIO.

9.1 Error Priority
For each IP, ERROR should have priority over DONE for the same operation. Once an error is latched, BUSY shall clear and the IP shall return to an idle/error state until software resets or clears the error according to the implemented policy.
10. Reset Behavior
Reset places the RISC-V-visible control/status registers into known default values.
CNN, Distance Engine and DMA enter IDLE with BUSY=0, DONE=0 and ERROR=0.
Pending completion interrupts are cleared on reset.
No DMA transfer shall be active after reset.
Memory contents are not assumed to be initialized by accelerator reset unless explicitly implemented.
Software must configure base addresses, dimensions, metric, reference count and threshold before starting processing.

12. Detailed End-to-End Data Flow
Input image, CNN weights and reference embeddings reside in DMEM or are placed there before accelerator execution.
DMA may transfer the input image and CNN weights to the CNN input/data interface as configured.
CNN reads the image/weights and executes INT8 convolution.
Pooling reduces the feature representation.
The embedding buffer stores the fixed-length generated embedding.
Generated embedding is written to DMEM at EMBED_BASE_ADDR.
Distance engine reads the generated/query embedding and reference embeddings.
For each reference, the configured distance metric is calculated.
The minimum distance is selected.
Minimum distance is compared with THRESHOLD.
The engine outputs MATCH or ANOMALY and asserts SCORE_DONE_IRQ.
RISC-V reads the result and can report it through UART/GPIO.
13. Software / Firmware Responsibilities
Initialize memory/peripherals and clear accelerator status.
Program CNN register set.
Program DMA source/destination/length and start DMA where required.
Wait for DMA completion using IRQ or polling.
Start CNN and wait for ACCEL_DONE_IRQ or CNN_DONE polling.
Program distance-engine query/reference addresses, reference count, metric and threshold.
Start distance engine.
Handle SCORE_DONE_IRQ or poll DIST_STATUS.
Read RESULT and MIN_DISTANCE.
Transmit final result through UART and/or drive GPIO.

15. Kiro Implementation Requirements
Kiro should use this document as the primary functional specification and follow these implementation rules:
Do not change the top-level functional architecture without explicitly flagging the change.
Implement the 32-bit memory-mapped system-bus abstraction and a 2-master × 8-slave address-decoding interconnect.
Use the faculty-provided RISC-V core unchanged unless integration requires a documented adapter.
Treat DMA as both a memory-mapped slave for CPU configuration and a secondary bus master for bulk transfers.
Keep CNN datapath and Distance/Anomaly datapath modular and independently testable.
Use INT8 data for image/weights/embeddings as specified.
Keep control/status registers memory mapped.
Implement DONE/ERROR latching and the three named interrupts.
Preserve the memory-map base addresses and region sizes defined in Section 3.
Add assertions for invalid addresses, illegal starts while BUSY, invalid configuration and DMA errors.
Create self-checking testbenches and compare accelerator outputs against Python/NumPy golden-model results.
Where this document marks a register detail as proposed, verify compatibility with faculty-provided templates before final RTL freeze.

17. Design Constraints and Assumptions
The project targets a compact embedded image-processing workload suitable for a two-month academic implementation.
Input/weights/embedding data are INT8.
DMEM capacity is 64 KB.
The CNN is lightweight; exact layer count, dimensions and embedding length must be selected so that the design fits the available memory/resources.
Reference embeddings are stored in DMEM for the baseline implementation.
The distance metric is programmable, but the exact supported metric set must be finalized in RTL; a simple integer metric is preferred for implementation simplicity.
The threshold is programmable.
Exact AXI signal-level adaptation is an implementation detail of the faculty-provided interconnect wrapper and must not alter the logical memory map.

19. Source Basis and Change Note
The uploaded specification document establishes the project title, system purpose, three project-specific IP blocks, objectives, and the control/data-path diagrams. In particular, the source document states that the system provides memory-mapped access to peripherals, supports INT8 processing, DMA transfers, interrupt completion and Python/NumPy verification.
The supplied page-3 architecture image labels the bus as a 'System Bus / Interconnect (AXI-Lite style, memory-mapped)' and page-4 labels it as 'SYSTEM BUS (32-bit Memory Mapped)'. For consistency with the current project decision, this specification uses '32-bit Memory-Mapped System Bus' as the conceptual architecture term. AXI terminology is retained only for the faculty-provided RTL interconnect-generation script.
